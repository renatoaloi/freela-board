# DB Migrations

## ADDED Requirements

### Requirement: Schema versioning via Alembic
The system SHALL use Alembic as the single source of truth for database schema versioning. All schema changes MUST be tracked as versioned migration scripts in `backend/alembic/versions/`.

#### Scenario: Initial migration exists on startup
- **WHEN** the application starts for the first time with an empty database
- **THEN** Alembic SHALL run all pending migrations and create all tables defined in `app/domain/models.py`

#### Scenario: Subsequent migration applied on startup
- **WHEN** a new migration script is added to `backend/alembic/versions/`
- **THEN** the application SHALL apply it automatically on next startup via `alembic upgrade head`

#### Scenario: No migration to run
- **WHEN** all migrations are already applied and the database is up-to-date
- **THEN** the application SHALL start normally without errors

### Requirement: Automatic migration on application startup
The FastAPI lifespan SHALL invoke `alembic upgrade head` via the Alembic Python API (`alembic.config` + `command.upgrade`) before the application serves requests.

#### Scenario: Migration runs during lifespan startup
- **WHEN** the FastAPI application starts
- **THEN** the lifespan SHALL run `alembic upgrade head` before the yield point

#### Scenario: Migration failure prevents startup
- **WHEN** a migration fails to apply
- **THEN** the application SHALL fail to start with a clear error message

### Requirement: Database URL alignment
The Alembic configuration SHALL use the same `DATABASE_URL` as the application's `Settings` class, not a hardcoded value.

#### Scenario: env.py reads from settings
- **WHEN** Alembic runs (via CLI or application startup)
- **THEN** `env.py` SHALL read `sqlalchemy.url` from `app.core.config.settings.DATABASE_URL`
- **AND** SHALL ignore the hardcoded value in `alembic.ini`

### Requirement: SQLite compatibility via batch mode
The Alembic environment SHALL enable `render_as_batch=True` to support ALTER TABLE operations on SQLite.

#### Scenario: Batch mode enabled in env.py
- **WHEN** Alembic runs any migration against a SQLite database
- **THEN** `env.py` SHALL configure the context with `render_as_batch=True`

### Requirement: Workflow for creating new migrations
Developers SHALL create new migrations by modifying models and running `alembic revision --autogenerate -m "<description>"`, followed by reviewing the generated script.

#### Scenario: Autogenerate new migration after model change
- **WHEN** a developer modifies `app/domain/models.py` to add, remove, or change a column
- **AND** runs `alembic revision --autogenerate -m "description"`
- **THEN** Alembic SHALL generate a migration script in `backend/alembic/versions/` reflecting the schema diff

#### Scenario: Migration script reviewed before commit
- **WHEN** a migration script is autogenerated
- **THEN** the developer SHALL review and verify the generated script before committing it to version control

### Requirement: No Base.metadata.create_all() in production path
The application SHALL NOT use `Base.metadata.create_all()` as a schema management mechanism. Schema changes MUST go through Alembic migrations only.

#### Scenario: create_all removed from lifespan
- **WHEN** the application starts
- **THEN** the lifespan SHALL NOT call `Base.metadata.create_all()`
- **AND** SHALL NOT execute raw ALTER TABLE statements
